# Production payment and delivery state foundation

**Code-only foundation. No production payment, founder approval, or delivery routes are mounted. All runtime gates remain closed.**

## Schema and invariants

Migration `0002_create_payment_delivery_state.sql` is separate from the order intake migration. `production_orders.status` retains its database check requiring `AWAITING_PAYMENT`; the new production state lives in separate payment/fulfillment tables. A database trigger seeds a locked `AWAITING_PAYMENT` state row when an order is inserted, without changing the existing order API response or token/idempotency logic.

- `production_payment_claims`: one globally unique HMAC digest per claimed transaction reference, encrypted reference text, saved order method, server amount/currency, and claim status. An order bearer token is verified by the service before claim insertion; raw tokens are not written.
- `production_settlement_evidence`: a founder-observed settlement record with HMACs for transaction reference, recipient and payer identity, plus method, amount, currency and evidence source. Its reference digest is globally unique within settlement observations. It is evidence, not approval.
- `production_payment_fulfillment_state`: one guarded state row per order. Valid payment path is `AWAITING_PAYMENT → UNDER_REVIEW → PAYMENT_CONFIRMED` or `PAYMENT_REJECTED`; a rejected order may return to review on a new claim. Fulfillment path is `LOCKED → READY_TO_DOWNLOAD → REVOKED`.
- `production_founder_approval_decisions`: one decision per claim, at most one approval per order, and approval requires linked settlement evidence. Decisions record founder identity, reason and time.
- `production_third_party_payer_exceptions`: an audited spouse/relative/other relationship and rationale tied to the specific order, claim, and evidence. It records an exception only; a founder must still explicitly approve.
- `production_download_grants`: at most one grant per order. A composite foreign key requires an `APPROVE` decision. Triggers require the order to be approved and ready before grant insertion, and prevent reactivation after revocation.
- `production_payment_audit_events`: event history with database triggers rejecting updates and deletes.

Foreign keys, unique indexes, check constraints, triggers, transactions and `SELECT … FOR UPDATE` guards provide multiple layers against duplicate references, invalid state changes, conflicting/repeated decisions, and concurrent grant issuance. Claims and settlement observations are never a paid state. Customer references/screenshots cannot insert approval decisions or grants.

The service functions in `payment_state.py` are not wired to `production_checkout/app.py`. Founder functions require an actor identifier, but that identifier must come only from a future MFA-authenticated server session; a caller-supplied value alone is not authentication.

## Third-party payments

Ordinary order creation continues to collect only the existing customer details; no payer field was added. The founder compares an HMAC of the buyer phone with the independently observed payer identity. If they differ, approval is blocked until a founder documents a relationship category and reason through the manual-exception operation. The exception does not bypass reference, method, recipient, amount, currency or evidence matching. The founder still records a distinct approval decision.

## Privacy and recovery

The existing customer order token remains generated by the independent API and stored only as an HMAC hash. Claims verify that original token before insertion. Transaction references and evidence notes are represented as ciphertext fields; the future HTTP integration must use a managed encryption key, redact these values from logs, and keep the private recovery code selectable/copiable and safely hideable in the approved account-free recovery flow. No account or password is introduced.

## Migrations and tests

Apply in order:

1. `0001_create_orders.sql`
2. `0002_create_payment_delivery_state.sql`

Rollback only the foundation with `0002_rollback_payment_delivery_state.sql`; it removes the added state artifacts and restores the order-table comment without dropping or rewriting `production_orders`. The acceptance workflow applies both migrations to disposable PostgreSQL, runs production order, state, R2-adapter and staging-backend regressions, rolls back 0002, confirms 0001's order table remains, then reapplies 0002.

Tests do not contact a payment provider, R2, Render, the public checkout, or production data. Synthetic founder IDs and fictional recipient fingerprints are test-only values.

## Not implemented / release blockers

- No HTTP customer claim, founder MFA, settlement verification, approval, recovery, grant, or download routes are mounted.
- No founder session, MFA enrollment/recovery, CSRF protection, role policy, or authentication/audit integration exists yet.
- The future reference-encryption implementation and key management must be reviewed and tested; the database expects ciphertext but does not encrypt it itself.
- No live bank/Telebirr ledger integration exists. Manual evidence needs a controlled evidence-retention and review procedure.
- Customer notification, refund handling, privacy retention/deletion, rate-limiting, R2 delivery, backups, and restore acceptance remain separate launch work.
- Payment, intake, founder approval and delivery gates remain disabled. No real approval or order processing is authorized.
